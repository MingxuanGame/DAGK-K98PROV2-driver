## 2. udev 规则验证（成功，并发现一个真实坑）

第一次用 `/etc/udev/rules.d/99-dagk-k98pro.rules`：

```
$ getfacl -p /dev/hidraw2
user::rw-          # 只有基础项, 没有给登录用户加 ACL
group::rw-
other::---
$ python3 -c "open('/dev/hidraw2','r+b')"
PermissionError: [Errno 13]
```

`udevadm test` 显示规则匹配、标签也加上了：

```
hidraw2: /etc/udev/rules.d/99-dagk-k98pro.rules:3 MODE="0660": Set mode: 0660
Current Tags: uaccess
CURRENT_TAGS=:uaccess:seat:
```

但 73-seat-late.rules 的 `RUN{builtin}+="uaccess"` **从没匹配到**（udevadm test 里根本没有这一行）。
原因：`uaccess` 标签是在 `99-` 文件里加的，而处理它的内置程序在 `73-seat-late.rules`（先执行），
所以内置程序检查标签时标签还不存在。

改成 `/etc/udev/rules.d/70-dagk-k98pro.rules` 后（重新 reload + 重新绑定 USB）：

```
$ getfacl -p /dev/hidraw2
user::rw-
user:mingxuangame:rw-      <-- ACL 出现了
$ python3 -c "open('/dev/hidraw2','r+b')"
打开成功
```

结论：**自定义 udev 规则要用 `TAG+="uaccess"` 时，文件名必须排在 `73-seat-late.rules` 之前（如 `70-`）。**
仓库里的 `70-dagk-k98pro.rules` 就是修正后的版本。

## 4. 第二轮真机测试（接收器 3151:5006）—— 重要更正与新发现

第一轮结论"设备无响应"是**我的测试工具写错了**，不是设备的问题。以下是更正与实测结果。

### 5.1 更正：第一轮的"全 0"是工具 bug

Linux hidraw 的两个 ioctl 号不同：

| 宏 | 值 | 用途 |
|---|---|---|
| `HIDIOCSFEATURE(len)` | `0x06` | **发送** SET_FEATURE |
| `HIDIOCGFEATURE(len)` | `0x07` | **读取** GET_FEATURE |

我第一轮的脚本两个方向都用了 `0x07` —— 等于**只读不写**，设备根本没收到命令，所以永远读到全 0。
这个 bug 让我一度误判"设备/通道有问题"，也误导了你。修正后设备立刻就有响应。

另外：本设备报告描述符里没有 Report ID，Linux `usbhid` 对 `report number == 0` 会做
`buf++ / count--`，所以 ioctl 长度要用 **65**，设备才会正好收到 64 字节报文。

### 5.2 实测：2.4G 接收器 F7 链路状态（解码全部命中）

修正后的第一次读取就拿到实时数据：

```
$ python3 tests/hidraw-test.py --pid 0x5006
设备 /dev/hidraw2   0003:3151:5006.0014   iface=6-1.1:1.2
报告描述符 06 FF FF 09 02 A1 01 09 02 15 80 25 7F 95 40 75 08 B1 02 C0

=== [接收器] 0xF7 链路状态 ===
  原始: 00 64 00 00 01 01 01 00 00 00 00 00 00 00 00 00
  ✓ 接收器响应 0xF7
  键盘电量=100%  对象=键盘  键盘在线=True  可发送=True  可读取=False
```

对照逆向出来的解码表，**每个字段都对上了**：

| 字节 | 逆向含义 | 实测 | 判定 |
|---|---|---|---|
| r[0] | isCanRead (`===1`) | 0 | 当时确实没有待读数据 ✓ |
| r[1] | 键盘电量 | 0x64 = **100%** | ✓ |
| r[3]==0 | 键盘在线 | 0 | **在线** ✓ |
| r[5]==1 | isCanSend | 1 | **可发送** ✓ |
| r[6] | 目标掩码 (1键盘/2鼠标/3键鼠) | 1 | **键盘** ✓ |

→ 2.4G 的握手协议与字段解码**在真机上得到验证**。

### 5.3 新发现：这个接收器的厂商通道很"脆"

1. **时序敏感**：发送后固定延迟读取，实测 **5ms / 20ms 成功，50ms 超时**。
   原厂代码里 `INTERVAL_24G_TIME = 10` 不是随便写的 —— 必须贴着 10ms 走。
2. **必须走完整握手**：跳过 `F6 选目标` / `FC 通知读取` 直接发命令，接收器会把控制端点 stall 掉，
   之后所有访问返回 `EPIPE (Broken pipe)`，严重时设备直接重新枚举（`ENODEV`）。
3. **恢复办法**（不用拔插）：
   ```bash
   echo -n "6-1.1:1.2" | sudo tee /sys/bus/usb/drivers/usbhid/unbind
   sleep 1.5
   echo -n "6-1.1:1.2" | sudo tee /sys/bus/usb/drivers/usbhid/bind
   ```
   接口级重挂即可恢复；实在不行就拔插一次（设备自己也会重新枚举）。
4. **刚拔插后不要立刻发命令**：重新枚举后需要一点时间（键盘也要重新建立 2.4G 链路），
   这期间 F7 会超时。

> 我在测试过程中确实把接收器搞挂过两次，都是用上面的接口重挂 / 拔插恢复的，硬件没有损坏。

### 5.4 因此对网页驱动做的加固

- **所有 WebHID 读写都加了超时**（默认 1.5s）。原来没有超时，设备一 stall 页面就永久卡死。
- **接收器连接流程加了重试**：先 F7 读链路状态，再 `0x8F`（重试 3 次，间隔 400ms）。
- **后台状态轮询连续失败 2 次就自动停止**，并提示"接收器停止响应，请拔插一次" ——
  避免像我的脚本那样越轮询越死。
- **时序**：发送前/读取前各 10ms，与 `INTERVAL_24G_TIME` 一致。
- 「高级 / 诊断」页新增**列出浏览器已授权的 HID 设备**按钮，可直接看到 Chrome 到底拿到了哪些集合。

## 5. 第三轮：定位到"连上一会儿就断"的**自身代码 bug**

用户反馈"本地连接无线接收器失败，选择配对后一会就断联"。排查后确认是**网页驱动自己的 bug**，
不是设备的问题。

### 5.1 根因：事务结束后无条件重启后台轮询

`protocol.js` 的 `sendMsg` / `readMsg` 里有这样一段（错误版本）：

```js
if (this.mode === MODE.RF24G) {
  this.relay.stopPolling();
  try {
    return await this.relay.send(...);
  } finally {
    this.relay.startPolling(this.onStatus);   // ← 无条件重启
  }
}
```

连接时 `startPolling()` 被调用过一次，之后**每一次读写都会在 `finally` 里把它重新启动**，
等于永久维持一个"每 2 秒发一次 F7"的后台轮询。而 F7 是"SET + GET"两次控制传输 ——
对这个接收器来说，任何一次 GET 落在响应窗口之外都会让它 stall。于是：

```
连接成功 → 后台每 2 秒 F7 → 某次超时 → 接收器 stall → 全部 EPIPE → "断联"
```

**修复**：只在"本来就在轮询"时才恢复轮询（`wasPolling`），并且**默认根本不启动轮询**。

```js
const wasPolling = this.relay.isPolling;
this.relay.stopPolling();
try { ... } finally { if (wasPolling) this.relay.startPolling(this.onStatus); }
```

### 5.2 连接流程也改成保守策略

| 项目 | 旧行为 | 新行为 |
|---|---|---|
| 连接时 F7 | 最多 3 次重试 | **只发 1 次**，失败就提示拔插 |
| 连接时 0x8F | 自动发，重试 3 次 | **不发**，改由「读取设备配置」按需触发 |
| 后台轮询 | 自动开，2 秒一次 | **默认关**；需要时在「高级」页手动勾选（5 秒一次） |
| F7 读取等待 | 固定 10ms | **0ms**（交给 WebHID 往返时延，实测 50ms 必挂） |
| 轮询失败 | 重试 2 次才停 | **第一次失败就永久停**，提示拔插 |

界面「高级 / 诊断」新增三个控件：**刷新 2.4G 链路状态**、**每 5 秒自动刷新（默认关）**、**软复位 HID 连接**。

### 5.3 顺带修掉的两个测试夹具 bug（会让测试"假通过/假失败"）

1. **浏览器夹具 `tests/fake-hid.js` 的 `0xFC` 空实现**：真实接收器在收到 FC 后会把"键盘最近一条应答"
   放进读取缓冲；夹具直接 return，导致读回的是上一条 F7 状态帧。已按真实语义修正。
2. **夹具把 F7 的状态应答也当成"键盘应答"缓存**：F7/F6/FC/FE 都是接收器**本地**控制帧，不经过键盘，
   不能更新键盘应答缓存。否则 FC 之后读到的是 F7 的状态帧（现象：第 0 页首字节是 1 而不是 0）。
   已加 `DONGLE_LOCAL` 白名单排除。

这两个 bug 解释了为什么"单测全绿但真机/端到端读出来的矩阵是错的"。现在已补上回归测试：

- `2.4G: 经接收器读按键矩阵 (0x8A 全 8 页) 数据正确`
- `2.4G: 读矩阵不会把 F7 状态帧当成键盘应答`
- `2.4G: sendMsg/readMsg 不会意外启动后台轮询`

### 5.4 测试数据（Node 逐帧追踪）

### 5.5 现在的加固清单（替代 5.4 旧清单）

- 所有 WebHID 读写 **1.5s 超时**（原来会让页面永久卡死）。
- 2.4G 默认**不做后台轮询**；连接阶段只发 1 次 F7、不发 0x8F。
- 轮询第一次失败即永久停止并提示。
- F7 的 SET→GET 不再额外等待（实测 50ms 必挂，10ms 也有风险）。
- `ensureCanSend/ensureCanRead` 重试次数 5 → 3。
- 「高级 / 诊断」提供：刷新链路状态 / 自动刷新开关 / 软复位 HID / 列出已授权设备。

## 6. 第四轮："点「读取设备配置」键盘就断联"的原因与修复

### 6.1 原因：8 页连发，且"一页失败还继续打剩下 7 页"

「读取设备配置」要读 8 页（`0x8A` × 8）。旧实现里每一页都会走
`send()` → `ensureCanSend()`（最多 3 次 F7 轮询）+ `send()` → `read()` → `ensureCanRead()`（最多 3 次 F7 轮询），
一页 6～8 次控制传输，8 页就是 **50 次左右**，而且：

```js
// 旧实现: 读不到就用 0 填, 继续下一页
for (let page = 0; page < 8; page++) {
  const r = await this.commonMsg(f, CK.Bit7);
  if (r) out.set(...);          // ← 失败也不停
}
```

只要某一页开始失败，剩下的页还会继续猛打 —— 对这个接收器就是雪上加霜，直接把链路打死，
现象就是**点一下读取，键盘就断联**。

### 6.2 修复

1. **新事务模型 `DongleRelay.transact()`**：一次事务只做
   `1 次 F7 预检 → 发命令 → 最多 3 次(间隔 150ms)等 isCanRead → FC → 读取`，
   一页从 6～8 次控制传输降到 **≤6 次**，正常路径只有 4 次。
2. **分页读取改成"失败即中止"**：任何一页失败立刻抛出，**不再请求后面的页**，
   并把失败信息明确显示给用户（"读取中断：… 已停止后续请求，避免把接收器拖死"）。
3. **页与页之间插 120ms 间隔**（2.4G 下），不再背靠背连发。
4. **宏读取遇到结束标记就收工**，不再把剩下的页白打一遍。
5. 界面加了**进度显示**（读取中 3/8 …）和**单页探测**（「高级 / 诊断」→ 选页 → 只读这一页），
   方便逐页定位到底是第几页开始出问题。

### 6.3 回归测试（防止再犯）

- `2.4G: 某一页失败时立即中止, 不再把剩下几页打完` —— 模拟第 3 页无响应，
  断言**没有请求第 4 页及以后**。
- `2.4G: 一页只做 1 次预检` —— 断言一页最多 2 次 F7、恰好 1 次 FC。

### 6.4 如果还是断

请用「高级 / 诊断」里的**单页探测**从第 0 页开始逐页点：

| 现象 | 说明 |
|---|---|
| 第 0 页就失败 | 链路本身不稳（键盘睡眠 / 距离 / 电量），先按一下键盘再试 |
| 前几页正常，第 N 页开始失败 | 接收器被连续读取拖垮 —— 请把「页间间隔」再调大，或只按需读单页 |
| 单页都正常，8 页连读失败 | 说明需要更长间隔 / 分次读取，可以一页一页手动读 |

## 7. 第五轮：断联的**真正根因**（接收器在"没有键盘"时的行为）

前面几轮一直在改时序、轮询、中止策略，但用 usbmon 抓包 + 状态轮询之后，根因终于清楚了。

### 7.1 usbmon 抓到的真实现象

一次成功的 F7 之后，紧接着的下一次 SET_FEATURE 直接返回 `-2 (ENOENT)`，同一时刻中断端点也 `-2`：

```
S Co:6:027:0 s 21 09 0300 0002 0040 64 = f7000000 00000008 ...   <- SET 成功
C Co:6:027:0 0 64 >                                              <- 状态 0 (成功)
S Ci:6:027:0 s a1 01 0300 0002 0040 64 <
C Ci:6:027:0 0 64 = 00640000 01010100 ...                        <- GET 成功 (数据有效)
S Co:6:027:0 s 21 09 0300 0002 0040 64 = f7000000 ...
C Co:6:027:0 -2 64 >                                             <- -2 = ENOENT
C Ii:6:027:3 -2:1 0                                              <- 中断端点也 -2
```

配合 dmesg：`usb 6-1.1: USB disconnect, device number 26` → `new full-speed USB device number 27`。

**结论：不是 stall，是接收器自己把 USB 断了并重新枚举。**（dmesg 里累计 16 次 disconnect，全是我测试期间造成的。）

### 7.2 为什么它会自己断

对照它上报的链路状态就清楚了：

| 时刻 | F7 读数 | 含义 |
|---|---|---|
| 键盘开着、在 2.4G 档时 | `00 64 00 00 01 01 01 00` | 电量 100%、**在线**、目标=键盘 → 命令能转发 |
| 键盘关掉/休眠/不在 2.4G 档时 | `00 00 00 01 01 01 00 00` | 电量 0、**不在线**、**目标=0** → 没有任何设备可转发 |

**接收器在"没有可用键盘"时，对厂商配置请求最终会以"断开重连"收场。**
它只是一个 RF 转发器：没有配对设备时，厂商通道的请求无处可去，固件就把 USB 挂断重来。

这也解释了之前所有"莫名其妙"的现象：

* 为什么单测全绿、真机第一次 F7 也有数据 —— 那时键盘确实在线；
* 为什么后来怎么改时序都不行 —— 键盘不在线，任何命令都注定失败；
* 为什么软件层 unbind/bind 有时"恢复了"却依然读不到数据 —— USB 回来了，但键盘还是没连上。

### 7.3 由此得到的正确用法（也是网页现在的行为）

1. **接收器必须配着一台已开机、且在 2.4G 档的键盘**才有意义；键盘不开机，网页做什么都没用。
2. 网页在 `transact()` 里**先查 F7**：不在线就直接抛"键盘不在线（可能睡着了）"并中止，
   **绝不继续发命令** —— 因为继续发正是把它搞断的原因。
3. 掉线/超时统一走通知通道提醒用户，不再盲目重试。

### 7.4 顺带确认：软件方式无法给这个接收器做真正的"重新插拔"

* 接口级 `unbind/bind`、整设备 `authorized 0→1`、`USBDEVFS_RESET` —— 都只能重新枚举 USB，
  **不能复位接收器 MCU**（VBUS 没断），所以楔死之后这些手段都救不回来，只有**物理拔插**有效。
* 端口断电（`uhubctl` 那类）也不行：接收器挂在一个普通 USB2.0 HUB（`214b:7250`）上，
  廉价 hub 不支持 per-port power switching。

所以现在按你说的方案：**掉线 → 系统通知你 → 你物理拔插**。

## 8. 第六轮：**接收器硬件故障**的确诊（结论性）

### 8.1 决定性实验：静置 60 秒不碰它

```
基线 USB 事件行数 = 49
静置 60 秒（完全不访问设备）
之后 = 54   ← 新增 5 条, 全是接收器自己的断开/重连
```

同一个 `USB2.0 HUB` 上，别的设备一次都没掉过。**所以不是 HUB、不是供电、不是驱动，是接收器本身。**

### 8.3 这解释了之前所有的"怪现象"

| 现象 | 真正的解释 |
|---|---|
| 你最初说"选配对后一会就断联" | 接收器每 15～30 秒自己重置一次 —— 与网页无关 |
| 真机测试第一次 F7 有数据、之后就没有 | 刚好赶上它一次"活着"的窗口 |
| 改时序 / 改轮询 / 改中止策略都没用 | 因为根本不是软件问题 |
| 软件 unbind/bind 有时"恢复"了却读不到数据 | USB 回来了，但 MCU 仍在故障状态 |
| `error -110` / `error -71` | 典型硬件/接触/供电级失败 |

### 8.4 建议（按性价比排序）

1. **换一个 USB 口，直插主机**（不要走那个 HUB）—— 有些边缘设备换个口就稳了，这是最便宜的一步。
2. **优先用有线连接**（`3151:5002`）做配置 —— 网页完整支持，且是有线才稳定的路径。
3. 若换口无效，**这个接收器需要更换**（USB 层已经无法枚举，属于硬件损坏）。
